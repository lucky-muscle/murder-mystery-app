# 作品説明資料：名前だけが生きている

## 作品概要

本作品は、5人用マーダーミステリーをWeb上で進行するためのゲーム支援ツールである。キャラクター選択、ゲームフェーズ管理、プレイヤー別の情報表示、議論・推理・投票、エンディング表示までを一連の流れとして実装した。

マーダーミステリーでは、プレイヤーごとに閲覧できる情報や、進行中に開示される情報が異なる。そのため、本作品では現在のゲームフェーズ、選択中のキャラクター、進行状況に応じて表示内容を切り替える構成にした。これにより、プレイヤーが次に行う操作を把握しやすくし、情報の誤表示やネタバレを防ぎながら進行できるようにしている。

また、ゲームを円滑に進めるため、GMが進行状況を管理できる仕組みも実装した。GM側ではフェーズの切り替えや進行状況の確認を行えるようにし、プレイヤー画面とは別に、ゲーム全体を制御する役割を持たせている。これにより、プレイヤーごとの表示制御と、GMによる進行管理を分けて扱える構成にした。

なお、ネタバレ防止のため、シナリオ本文、調査カードの具体的な内容、エンディングの詳細は非公開としている。現在は、ゲーム進行管理や画面遷移などのシステム面のみ確認できる状態である。

## 操作方法

本作品の基本的な操作手順は以下の通りである。

1. タイトル画面からゲームを開始する。
2. プレイヤーごとにキャラクターを選択する。
3. 作品概要および進行説明を確認する。
4. ゲームフェーズに従って調査画面へ進む。
5. カードを選択し、議論情報を確認する。
6. 推理画面で各プレイヤーの推理内容を確認する。
7. 投票を行い、結果に応じたエンディングを表示する。

プレイヤーが次に何をすればよいか分かりやすくするため、画面上では現在のフェーズや操作可能な内容が分かるように構成した。

## 実装した主な機能

本作品では、マーダーミステリー特有の複雑な進行や情報管理をWebアプリ上で一元化し、GMとプレイヤーが円滑にゲームを進行できることを目指した。

React・TypeScript・Firebaseを使用し、複数端末間でのリアルタイム同期、キャラクター別の情報表示、調査カードの取得・共有、ゲーム進行管理などを実装した。

### ルーム作成・参加機能

GMがルームを作成し、参加者が共有されたルーム番号を入力して参加できる機能を実装した。

ルーム番号は英数字で管理し、入力時には自動的に大文字へ変換する。また、最大8文字の入力制限やEnterキーによる参加操作、未入力時の参加ボタン無効化など、操作性を考慮した設計とした。

参加者は入室時に名前を設定でき、同じルーム内での名前の重複を検知する機能を実装した。

また、キャラクター振り分けの段階までは参加できる一方、オープニング開始後は新規参加を制限し、ゲーム進行中に参加者構成が変化することを防いでいる。

さらに、ルーム番号や参加者名、プレイヤー情報をブラウザのセッションストレージに保存し、画面の再読み込み時にも参加状態を復元しやすい構成とした。

### キャラクター振り分け機能

GMが参加者にキャラクターを割り当てる機能を実装した。

GMの画面には参加者ごとのキャラクター選択欄が表示され、各参加者の担当キャラクターを設定できる。

全参加者への割り当てが完了していない場合や、同一キャラクターが重複して割り当てられている場合は、次のパートへ進めないようにした。

これにより、役割の設定ミスを防止している。

参加者側では、GMがキャラクターを振り分けている間は専用の待機画面を表示する。振り分け完了後は、自分のキャラクター情報を確認できる構成とした。

### ゲームパート管理

本作品では、ゲーム全体を以下の流れで管理している。

1. 入室待機・キャラクター振り分け
2. ルール説明・作品概要・キャラクターシート配布
3. 議論前半
4. 休憩
5. 議論後半
6. 推理
7. 投票
8. エンディング・解説

GMは各パートに用意された操作ボタンから、ゲームの進行状況を切り替えられる。

参加者の画面はGMが変更した進行状態に応じて自動的に更新されるため、参加者ごとに画面遷移を操作する必要がない。

また、画面右側にはスケジュールを常時表示し、現在のパートを強調することで、参加者がゲーム全体の流れを把握しやすい構成とした。

### 捜査資料の表示・配布機能

ゲーム中に使用する資料を「捜査資料」として一元管理する機能を実装した。

管理対象には、ルール説明シート、作品概要シート、キャラクターシート、見取り図、追加情報シート、調査カード、特別調査シート、エンディングシートなどが含まれる。

GMはすべての資料を閲覧できる一方、参加者には、自分に配布された資料や閲覧権限のある資料のみを表示する。

資料の配布では、ルール説明シート、作品概要シート、キャラクターシートの順に確認できるようにし、適切な順序で情報を公開できるようにした。

また、GMは特定の参加者への個別配布や、資料の全体公開を操作できる。

配布された資料は画面左側の捜査資料一覧からいつでも再表示でき、プレイヤーが情報を確認しながら推理を進められる。

### 資料閲覧ウィンドウ機能

捜査資料を画面上の独立したウィンドウで表示する機能を実装した。

ウィンドウはマウス操作によるドラッグ移動に対応しており、ゲーム画面を確認しながら任意の位置に資料を配置できる。

また、資料の拡大・縮小や全画面表示にも対応し、複数ページのシートについてはページを切り替えて閲覧できる。

スマートフォンでは画面サイズに合わせて閲覧方法を調整し、PCとスマートフォンの双方で資料を確認しやすい構成を目指した。

### 調査マップ機能

議論パートでは、横7列・縦4行の合計28マスからなる調査マップを表示する。

各列は5人のキャラクター、被害者の様子、山荘の様子に対応しており、列ごとに色を割り当てることで調査対象を視覚的に区別できるようにした。

調査カードは初期状態では各列の1段目のみ取得可能とし、カードを取得すると、その上下左右に隣接するマスが新たに取得可能になる仕組みを実装した。

また、自分のキャラクターに対応する列のカードは取得できないよう制御している。

取得できるカードは、調査マスの解放状態、取得済みかどうか、現在の手番、調査の開始状態などの条件に基づいて判定される。

これにより、ゲームのルールに沿った調査進行をWebアプリ上で再現した。

### 調査順・調査カード取得機能

調査は参加者が順番にカードを取得する形式とし、GMが調査開始前に参加者の調査順を決定できるようにした。

調査順に重複や不足がある場合は確定できないようにし、全参加者が一度ずつ手番を持つ構成とした。

調査開始後、現在の手番に該当するプレイヤーのみが新しい調査カードを取得できる。

カードが取得されると、所有者の情報と次のプレイヤーの手番が更新され、次の参加者が調査できる状態になる。

取得済みカードには所有者のキャラクター固有色のマーカーを表示し、誰が取得したカードなのかを一目で判断できるようにした。

休憩中や推理パートでは新しいカードの取得を制限し、ゲームの進行状況に応じた操作制御を行っている。

### 調査カードの公開・共有機能

取得した調査カードには所有者を設定し、基本的には所有者本人のみが内容を閲覧できるようにした。

カードの所有者は、取得したカードを全体公開できる。全体公開されたカードは他の参加者も閲覧できるようになり、公開状態を示す表示が追加される。

また、GMはすべての調査カードを閲覧でき、必要に応じて個別の参加者へ閲覧権限を与えたり、全体公開状態を変更したりできる。

これにより、カードの所有者、閲覧権限、公開状態を分けて管理し、マーダーミステリーに必要な情報の非対称性を維持できるようにした。

### 密談・カード譲渡機能

GMが密談ボタンを押すと参加者一覧が表示され、密談する2名を選択できる。

密談中は、選択された2名の間で所有する調査カードを個別共有できるようにした。

個別共有ではカードの所有者を変更せず、密談相手だけに閲覧権限を与える。

また、単にカードを見せるだけでなく、カードそのものを密談相手へ譲渡する機能も実装した。

譲渡するとカードの所有者が変更され、調査マップ上に表示される所有者マーカーの色も譲渡先のキャラクター固有色に切り替わる。

密談終了時には一時的な閲覧権限を解除し、密談中にだけ成立する情報共有と、譲渡による所有権の移転を区別して管理している。

### 特別調査・追加情報の管理機能

通常の調査カードとは別に、特別調査シートやキャラクターごとの追加情報を管理する機能を実装した。

特別調査シートは独立した調査マップではなく、捜査資料の一部として管理している。

GMは捜査資料一覧から必要なシートを選択し、任意の参加者へ個別に配布できる。

また、資料ごとに公開状態や閲覧可能な参加者を管理することで、必要なタイミングに必要な情報を提供できる構成とした。

### 議論・推理・投票機能

議論は前半と後半に分かれており、途中に休憩パートを設けている。

議論中は調査マップや取得済みの資料を確認でき、プレイヤーが集めた情報をもとに推理を進められる。

議論終了後は推理パートへ進み、参加者が事件について考察をまとめる時間を設ける。

その後、投票パートへ移行し、参加者は犯人だと思う人物に投票する。

投票画面には参加者名と対応するキャラクター名を表示し、自分自身への投票はできないようにした。

また、投票確定前に確認画面を表示することで、誤操作による投票を防止している。

投票結果はFirebase Firestoreに保存され、GMは各参加者の投票状況と投票先を確認できる。

### エンディング・解説機能

エンディングシートは投票対象となる5人のキャラクターに対応した5種類を用意している。

投票終了後、システムが投票結果を集計し、最多得票者に対応したエンディングシートを決定する。

GMは投票結果と配布予定のエンディングを確認したうえで、エンディングシートを参加者へ配布できる。

エンディングに移行すると、参加者の捜査資料一覧に該当するエンディングシートが追加される。

また、それまで閲覧できなかった調査カードや特別調査シートも公開され、参加者全員が事件に関する情報を確認できる。

これにより、ゲーム終了後の真相解説や情報の振り返りもWebアプリ上で行えるようにした。

### UI・ユーザビリティの改善

本作品では、実際の参加者によるプレイテストのフィードバックをもとに、UIの視認性と操作性を改善した。

特に色分けを重視し、キャラクターごとに固有色を設定することで、役名や調査カードの所有者を直感的に判別できるようにした。

また、背景や装飾には低彩度の色を使用する一方、頻繁に操作する重要なボタンには比較的彩度の高い色を用い、操作対象が目立つよう調整した。

画面左側には捜査資料、右側にはスケジュールと参加者一覧を配置し、オープニング以降は一貫したレイアウトで操作できる構成とした。

さらに、調査順が決定した後は参加者一覧を調査順に並べ替え、現在の進行状況を把握しやすくした。

ホバー時の色の変化やフォーカス表示、ボタンの大型化、資料の全画面表示なども追加し、操作対象の分かりやすさを改善した。

PCだけでなくスマートフォンの実機でも動作や閲覧性を確認し、文字サイズやレイアウトの改善を行った。

### リアルタイム同期・データ管理

複数端末で同じゲームを進行するために、Firebase Firestoreによるリアルタイム同期を実装した。

ルームごとにドキュメントを作成し、参加者情報、キャラクター割り当て、ゲームの進行状態、調査カードの所有者、閲覧権限、投票情報などをまとめて管理している。

各端末はFirestoreの変更を監視し、GMや参加者が操作した内容を他の端末にも反映する。

また、データベースへのアクセス回数を抑えるため、調査カードの取得状態と次のプレイヤーへの手番更新を一度の書き込みにまとめる処理を実装した。

これにより、当該処理における明示的な読み書き操作を3回から1回へ、約67％削減した。

### 保守性・汎用性を考慮した設計

本作品では、シナリオ固有の情報とゲーム進行を管理する共通システムをできるだけ分離することを意識した。

キャラクター情報、調査カード、資料の画像パス、ゲームの進行フェーズなどをデータとして管理し、画面側から参照する構成としている。

これにより、キャラクター名の変更、調査カードの差し替え、シートの複数ページ化などに対応しやすくした。

また、資料のPDFからPNGへの変換やファイル参照の整理にも取り組み、異なる端末での表示や資料の追加・修正を行いやすい構成を目指した。

将来的には、シナリオデータを差し替えることで、ほかのマーダーミステリー作品にも共通システムを再利用できるようにすることを目標としている。

## 制作意図

本作品では、マーダーミステリー特有の「プレイヤーごとに持っている情報が異なる」「進行に応じて情報が開示される」「推理と投票によって結末が変化する」という構造を、Webアプリとして扱えるようにすることを目的とした。

紙の資料やGMの説明に依存しやすい進行をWeb上で整理することで、プレイヤーが現在の状況を把握しやすくなり、ゲーム進行の負担を軽減できると考えた。

## 開発手法について

本作品は、当初は友人同士で遊んでもらうことを目的に、紙媒体を用いたアナログ形式のマーダーミステリーとして制作を開始した。

キャラクターシート、調査カード、見取り図などを紙資料として用意し、実際にプレイヤーに遊んでもらう中で、ゲーム進行や情報量、調査カードの見せ方について確認を行った。

その後、対面だけでなくネット上でも遊べる形式に発展させるため、Webアプリとして進行できるプロトタイプを制作した。

現在のプログラムコードは、今後の本格的な開発に向けたたたき台であり、ゲーム進行管理、資料表示、調査カード管理、投票、エンディング表示などの主要な流れを確認できるプロトタイプとして位置づけている。

また、実際に遊んでもらった際に得られた意見やリフレクションをもとに、UIやゲーム進行の改善を行っている。

具体的には、プレイヤーが現在の進行状況を把握しやすくするためのスケジュール表示、配布資料を確認しやすくするための捜査資料機能、調査カードの取得状況を分かりやすくするためのマーカー表示などを追加・調整した。

開発にあたっては、実装方針やデザインの方向性を検討する際に生成AIを活用した。

ただし、生成AIの出力をそのまま採用するのではなく、私自身が仕様に合わせて内容を確認し、必要な修正や調整を行いながら開発を進めた。

通常の実装手順でも同等の機能を開発することは可能であるが、本作品では短期間で多くの機能を試作し、UIやゲーム進行の方向性を検証する必要があった。

そのため、生成AIを活用した試作と、自身による修正・統合を組み合わせる開発方式を採用した。

この方式により、複雑なゲーム進行やUIの改善案を短いサイクルで検証し、プレイヤーからの反応を反映しながら、ポートフォリオとして動作する形まで効率的に実装した。

## 今後の課題

本作品は現在、GMが進行管理を行うことを前提としたゲーム支援ツールとして実装している。

今後は、より多くのユーザが遊びやすい形にするため、GMがいなくても進行できる機能を追加したいと考えている。

具体的には、フェーズ遷移、資料配布、調査カードの公開、投票結果に応じたエンディング選択などをシステム側で自動化し、プレイヤーのみでゲームを進行できる構成を目指す。

また、本作品は将来的な商品化も視野に入れている。

そのため、今後は以下の点を改善していきたい。

* GMなしで進行できる自動進行機能の追加
* 複数端末でのリアルタイム同期
* セーブ機能の追加
* スマートフォン向けUIの改善
* プレイヤーが迷わず操作できるチュートリアル機能の追加
* テストプレイ結果に基づくUI・進行・情報量の調整
* 商品化を見据えたシナリオ、デザイン、システムの品質向上
